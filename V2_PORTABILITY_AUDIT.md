# V2 portability and bootstrap entry audit

This bounded audit covers the Product repository at baseline `9203147` and the current working tree needed to diagnose `RUNNER_NOT_CONFIGURED` (`Bootstrap orchestrator is not ready`). It inspected source references, configuration shape, and path metadata. It did not call MCP tools, providers, browser bridges, or workflow lifecycle operations. Credential values and state contents were not read.

## Finding

The original failure was an entry/composition mismatch, not evidence that the V2 reducer could not run. The initial failed/cached HOST registration pointed to the historical `research_supervisor_poc/scripts/workflow_mcp.py` launcher and exposed no environment-key values. That sibling facade and the Product default facade at baseline are the Core V1 seam. The V2 self-host harnesses prove direct `workflow_v2_controller.StageController` behavior, but they do not by themselves prove MCP `workflow_run` readiness.

The current machine registration has since been changed to the Product launcher with `RESEARCH_WORKFLOW_RUNTIME_CONFIG`; the attached tool process can still be an old cached HOST until it is reloaded. The canonical new Product STDIO invocation completed planning with `CONTINUE` for consultation `CONSULT-20260912-122248-37b75606`. The current Product worktree contains the bounded composition adapter and explicit MCP selection needed for a V2 entry path: `src/workflow_mcp.py:318-330` loads the runtime config and selects `ProductWorkflowRuntime` only when `lifecycle_version == "v2"`; `src/workflow_mcp.py:397-398` dispatches `workflow_run` directly to that V2 runtime. This is a composition boundary fix. It does not change the V2 reducer or authorize the legacy bootstrap path.

## Legacy state and import boundaries

The legacy composition module owns the V1 path. Its defaults are `.research/runtime-composition.json`, `.research/stage-state.json`, and `.research/integration` (`src/runtime_composition.py:35-39`). Its doctor path accepts an existing V1 state or explicit V1 contract and its builder assembles the V1 Stage/Core/provider/orchestrator objects (`src/runtime_composition.py:504-557,698-806`). `src/workflow_runtime.py:62-82` likewise names `.research/workflow-state.json` and imports the V1 `StageController`; the runtime maps `RUNTIME_COMPOSITION_NOT_READY` to the stable runner error at `src/workflow_runtime.py:740-755`.

The Product adapter shares the normalized config and bounded exception type (`src/product_workflow_runtime.py:21-23`) and reuses intake normalization at `src/product_workflow_runtime.py:177-197`. It does not import the V1 StageController or V1 orchestrator. It uses `src/workflow_v2_controller.py` directly (`:24-25`) and maps only the config default `.research/stage-state.json` to the V2 journal (`:69-80`). That mapping is a fresh-journal selection rule; it is not a copy or migration of old state.

## Source hardcodes and credential assumptions

The bounded literal scan found no machine-specific `D:/`, `D:\`, `C:/Users`, or `C:\Users` path in Product runtime source under `src`, nor in the Product schema. Fixed paths occur in historical phase scripts and test fixtures. The relevant historical examples are the phase-0 host/V2/attachment paths at `scripts/phase0_manifest.py:20-23` and Step 10 temporary receipt discovery at `scripts/step10_acceptance.py:46-48,226`. Tests also use synthetic Windows paths to verify sanitization and portability behavior; those are test data, not runtime discovery. The cleanup review retains the ten offline regression tests and the repeatable acceptance/regression scripts they use as ENGINE assets; generated self-host evidence remains HISTORY.

Runtime configuration assumes machine-local capabilities by name or configured path: `codex_executable`, `auth_mode`, `bridge_root`, `node_executable`, `profile_dir`, and transport/project scope (`src/runtime_composition.py:204-216`). The Product doctor verifies their presence and shape but does not infer a profile or secret from a machine-specific path (`src/product_workflow_runtime.py:107-121`). The installed HOST registration is therefore an external deployment dependency, not repository state.

## Minimal repair recommendation

Keep the V2 adapter as the Product bootstrap/composition repair. The machine registration now points at the Product launcher and `RESEARCH_WORKFLOW_RUNTIME_CONFIG`; reload the attached cached MCP process, then use a fresh consultation to establish browser identity and receipt provenance. Supply an existing, non-secret runtime config with explicit `lifecycle_version: "v2"`, the external bridge and Node/profile locations, and the saved ChatGPT Codex runtime. Do not enable the V1 bridge, require `.research/stage-state.json`, copy legacy `.research` state, or change the V2 reducer. Date-fixed baseline/evidence producers and `implementation_evidence` should remain preserved under their owning engine-development project.
